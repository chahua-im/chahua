# Backend Restructuring & Cleanup Plan (2026-11-27)

This document captures the plan to reorganize `backend/` for readability, clearer feature ownership, and faster incremental development without changing runtime behavior during structural refactors.

## Current State & Problems

As of 2026-11-27, `backend/` contains **83,482 lines of Rust** across a single binary crate (`src/main.rs`, with no `lib.rs`):

| Layer / Area | Lines |
| --- | ---: |
| `src/services/` (excluding `services/api/`) | 43,881 |
| `src/rpc/` | 10,054 |
| `src/services/api/` | 9,283 |
| `src/handlers/` | 7,804 |
| `src/dto/` | 5,545 |
| `src/metrics/` | 1,222 |
| `src/schema/` | 683 |
| `src/utils/` | 580 |
| `src/config/` | 420 |

Four structural issues make the codebase difficult to navigate and maintain:

1. **Five to six horizontal layers per feature**
   Tracing one operation (such as `messages.send`) spans separate directory trees: `src/dto/` + `src/dto/rpc/`, `src/handlers/` + `src/openapi.rs`, `src/rpc/methods/` + `src/rpc/methods.rs` + `src/rpc/schema.rs`, `src/services/api/`, `src/services/` (split across 45+ top-level files/directories), and `src/models.rs`. The `services/api/` vs. `services/` split is an artifact of extracting HTTP handler code so JSON-RPC could reuse it, rather than a real domain boundary. As a result, closely related message logic is scattered across `services/api/chats/messages.rs`, `services/messages.rs`, `forwarding.rs`, `single_forwarding.rs`, `message_deletion.rs`, `message_visibility.rs`, and `system_messages.rs`.

2. **Dependency plumbing boilerplate (`AppInner`, `RpcServiceHandles`, and `*Deps` structs)**
   - `AppInner` (`src/state.rs`) and `RpcServiceHandles` (`src/rpc/mod.rs`) duplicate the exact same 17 service fields, copied field-by-field in `handlers/ws/mod.rs::rpc_services`.
   - `services/api/` defines **23 per-function `*Deps<'a>` structs** (8 in `services/api/chats/messages.rs` alone) that HTTP handlers and RPC method adapters reconstruct on every call.

3. **Mega-files with inline `#[cfg(test)]` blocks mid-file**
   Several core files combine multiple subdomains with hundreds or thousands of lines of tests—sometimes placed in the middle of production code:

   | File | Total lines | First `#[cfg(test)]` line |
   | --- | ---: | ---: |
   | `src/services/messages.rs` | 4,049 | 481 |
   | `src/services/unread/service.rs` | 2,532 | 1,111 |
   | `src/services/api/chats/messages.rs` | 1,868 | 609 |
   | `src/services/threads.rs` | 1,641 | 1,302 |
   | `src/services/social.rs` | 1,346 | 1,268 |
   | `src/models.rs` | 1,293 | 859 |
   | `src/services/client_tracking/mod.rs` | 1,240 | 802 |
   | `src/services/ws_registry/mod.rs` | 1,136 | 638 |
   | `src/services/link_previews/fetch.rs` | 1,126 | 494 |

4. **Dual-protocol evolutionary baggage and single-crate build cost**
   - `src/handlers/ws/mod.rs` (813 lines) retains the legacy ticket-WebSocket loop (~380 lines) duplicating watch forwarding, presence refresh, activity tracking, and `messageSync` driving alongside `src/rpc/session/`.
   - Full CRUD operations are maintained twice across HTTP (`handlers/` + `openapi.rs`) and JSON-RPC (`rpc/methods/` + `dto/rpc/` + `rpc/schema.rs`).
   - Compiling the entire backend as one binary crate slows incremental `cargo test` iteration and already hits macOS's 16 MiB `__eh_frame` linker warning.

## Design Principles

- **Vertical feature ownership**: Group a domain's service logic, queries, models, DTOs, and tests together instead of scattering them across `services/`, `services/api/`, `dto/`, and `models.rs`.
- **Startup-constructed domain services**: Construct feature services once at startup with only their narrow `Arc<...>` dependencies, eliminating per-call `*Deps<'a>` structs and eliminating duplicate `AppInner` / `RpcServiceHandles` wiring.
- **Sibling test modules**: Move `#[cfg(test)]` blocks over ~100 lines—and all mid-file test blocks—into sibling `tests.rs` or `tests/` modules (following the pattern in `src/rpc/session/tests/`).
- **Thin transport adapters**: Keep `handlers/` and `rpc/methods/` focused strictly on parameter extraction, transport mapping, and delegating to domain services.
- **Strict separation of refactor vs. behavior change**: Phases 1 and 2 must not alter wire shapes, SQL semantics, or HTTP/RPC behavior. Protocol removals belong exclusively in Phase 3 after client-compatibility verification.

## Phased Rollout Plan

Each phase is intended to land as small, reviewable PRs rather than a single branch-wide rewrite.

### Phase 1 — High-ROI Readability Wins (Zero Behavior Change)

1. **Extract `lib.rs` and move inline tests out of mega-files**
   - Add `src/lib.rs` so integration/unit code can share a clean crate boundary and `src/main.rs` shrinks to CLI dispatch + server startup; move `MAX_*_LIMIT` constants out of `main.rs` into their owning domains.
   - Move inline `#[cfg(test)]` suites out of the largest files (`services/messages.rs`, `services/unread/service.rs`, `services/api/chats/messages.rs`, `services/threads.rs`, `services/social.rs`, `models.rs`, `services/client_tracking/mod.rs`, `services/ws_registry/mod.rs`, `services/link_previews/fetch.rs`) into sibling `tests.rs` / `tests/` files.
   - Eliminate all mid-file `#[cfg(test)]` blocks where production code resumes below tests.

2. **Unify `AppInner` + `RpcServiceHandles` and remove `*Deps` structs**
   - Replace `AppInner` (`src/state.rs`) and `RpcServiceHandles` (`src/rpc/mod.rs`) with a single `ServiceContainer` / `AppServices` struct constructed once at startup and shared by both Axum HTTP handlers and `RpcSession`.
   - Convert free functions taking `*Deps<'a>` structs into methods on startup-constructed domain service structs (e.g., `MessagesService`, `GroupsService`, `StickersService`) that hold narrow `Arc<...>` dependencies, reducing HTTP handlers and RPC method wrappers to concise adapters.

### Phase 2 — Break Up Mega-Files & Collapse `services/api/`

1. **Consolidate the `messages` domain first** (highest complexity)
   - Merge `services/api/chats/messages.rs`, `services/messages.rs`, `forwarding.rs`, `single_forwarding.rs`, `message_deletion.rs`, `message_visibility.rs`, and `system_messages.rs` into one cohesive `messages/` module split by responsibility (`send.rs`, `history.rs`, `edit_delete.rs`, `forwarding.rs`, `metadata.rs`, `visibility.rs`, `system.rs`, `tests/`).
2. **Split `src/models.rs`**
   - Break the 1,293-line `models.rs` into domain modules (`models/messages.rs`, `models/chats.rs`, `models/users.rs`, `models/stickers.rs`, etc.).
3. **Collapse remaining `services/api/` splits feature-by-feature**
   - Unify `stickers`, `chats`/`unread`, `groups`/`members`/`invites`, `social`/`friends`/`blocks`, and `threads` into `features/<domain>/`, and move infrastructure modules under `infra/` and protocol adapters under `transport/`.

### Phase 3 — Remove Evolutionary Protocol Baggage (Gated on Client Support)

1. **Retire legacy ticket WebSocket**
   - Confirm no deployed PWA or Apple client builds still negotiate the legacy `{type, payload}` WebSocket protocol.
   - Remove the legacy `handle_socket` loop (~380 lines in `src/handlers/ws/mod.rs`), `parse_legacy_presence_watch`, dual `ServerWsMessage` serialization paths, and ticket-only frames (`MessageSyncHello`, `MessageSyncResumed`).
2. **Audit and remove redundant HTTP CRUD endpoints**
   - Keep HTTP strictly for multipart/binary uploads and media delivery, auth bootstrap, health/metrics, and `/external` service-token integrations; retire duplicate HTTP CRUD routes once all clients use JSON-RPC exclusively.
3. **Remove deprecated wire compatibility fields**
   - Retire `ListMessagesResponse::{next_cursor, prev_cursor}` and `SavedContent::Legacy` after verifying no active clients or stored rows require them.

### Phase 4 — Optional Cargo Workspace Split

Once `infra/`, `features/`, and `transport/` have clean acyclic boundaries:
- Split into workspace crates—for example `chahua-protocol` (DTOs, schemas, RPC wire framing), `chahua-core` (domain features, DB models/queries, infrastructure services), and `chahua-server` (Axum/HTTP/WS binary wiring)—to cut incremental `cargo test` compile times and resolve the 16 MiB `__eh_frame` linker warning.

## Verification Checklist (Per PR in Phases 1–2)

Run from `backend/`:
1. `cargo fmt -- --check`
2. `cargo clippy --all-targets --all-features -- -D warnings` (clean on all touched modules)
3. `cargo test` (DB-free unit tests pass) and `WETTY_TEST_DATABASE_URL=... cargo test` (full DB-backed suite passes)
4. Diff `--export-api-schemas` output against baseline to confirm zero unintended OpenAPI or OpenRPC schema changes.

## Non-Goals & Guardrails

- Do not attempt a big-bang rewrite across all 83k lines in one PR; keep each PR scoped to one file/module extraction or one domain slice.
- Do not mix behavioral changes, bug fixes, or protocol removals into Phase 1–2 structural PRs.
- Keep `backend/README.md` focused on current architecture rather than duplicating this plan or tracking per-PR progress here.
